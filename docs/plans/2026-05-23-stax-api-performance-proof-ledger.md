# stax-api Performance Proof Ledger

Status: active proof ledger
Date: 2026-05-23

## Purpose

This ledger prevents performance work from mixing three different claims:

- what the current `stax-xml` implementation has measured;
- what V8, JavaScriptCore, HotSpot, Woodstox, and quick-xml source evidence can
  prove;
- what remains an optimization hypothesis with possible counterexamples.

The target remains a StAX-like JavaScript reader that gives the best possible
throughput with bounded memory on large XML inputs in Node and browser
JavaScript runtimes. This document does not conclude that JavaScript runtimes
cannot exceed 200 MiB/s for the target shape. That conclusion is explicitly not
proved.

## Proof Vocabulary

| Term | Meaning | May support a final conclusion? |
| --- | --- | --- |
| `SOURCE_FACT` | Direct fact from current repository or upstream source code. | Yes, for code shape only. |
| `TRACE_FACT` | Generated bytecode, JIT, asm, profiler, or allocation evidence from a specific runtime/build. | Yes, but only for that runtime/build/input. |
| `BENCH_FACT` | Reproducible benchmark result with fixture, command, parity, memory, and environment recorded. | Yes, for that benchmark boundary. |
| `ENGINE_INVARIANT` | Runtime/language property backed by source or spec, such as engine-owned JS string storage. | Yes, but only for the exact invariant. |
| `NEGATIVE_RESULT` | A tried implementation line that failed under recorded gates. | No global conclusion; it narrows search space. |
| `COUNTEREXAMPLE` | Evidence that disproves a claim or forces a weaker claim. | Yes, to reject that claim. |
| `HYPOTHESIS` | Plausible explanation or direction that is not proven. | No. |
| `CONCLUSION` | Claim allowed in release docs only after all proof obligations are met. | Yes. |

Rules:

- A `CONCLUSION` must list its accepted evidence and known counterexample
  searches.
- `ENGINE_INVARIANT` about JS strings is not by itself a performance
  impossibility proof.
- `NEGATIVE_RESULT` for lazy getters, Buffer lanes, or value caches does not
  prove that all JavaScript runtime headroom is exhausted.
- Projection/selectivity wins do not prove full-materialization StAX wins.
- `byteFull` is an upper bound only when it avoids string materialization.
  `stringFull` remains the realistic parity metric for string-return claims.

## Current Evidence: Woodstox HotSpot Trace

`packages/benchmark/results/release/woodstox-hotspot-trace.md` is a
`TRACE_FACT` for the recorded boundary: Java/HotSpot, one 16 MiB fixture,
`warmups=4`, and `runs=1`.

The run uses the Java + Woodstox `XMLStreamReader` comparator and preserves the
same high-level full-string checksum contract as the JavaScript rows. It
reported 324.7 MiB/s, 967,967 events, and checksum `-746772258`, matching the
event/checksum results of the 16 MiB JavaScript object-shape and monomorphic
materialization runs.

The trace records HotSpot `PrintCompilation` and `PrintInlining` evidence around
`WoodstoxBench.consume`, Woodstox internals, and the accessor boundary. This is
evidence that the comparator ran under observed HotSpot compilation/inlining.
It is not an allocation profile and does not prove Woodstox internal object
lifetime, borrowed string lifetime, or the same object shape as a JavaScript
public event object.

## Current Evidence: Woodstox JFR Allocation Sampling

`packages/benchmark/results/release/woodstox-jfr-allocation.md` is a
`TRACE_FACT` for the recorded boundary: Java/HotSpot Temurin 8u472, Woodstox,
one 16 MiB fixture, JFR `profile` settings, `warmups=4`, and `runs=1`.

The run preserves the same high-level full-string checksum contract as the
external baseline and HotSpot trace: 967,967 events and checksum `-746772258`.
It reported 320.3 MiB/s during the JFR run, which is close to the non-JFR
Woodstox release baseline for the same fixture.

JFR reported 56 `ObjectAllocationInNewTLAB` samples and zero
`ObjectAllocationOutsideTLAB` samples. The report classifies 49 samples under a
`WoodstoxBench.consume` stack, 48 under a Woodstox stack, and 42 as
string-boundary samples. The top consume-stack sampled classes were `char[]`
with 32 samples / 2.0 KiB, `java.lang.String` with 10 samples / 240 B,
`com.ctc.wstx.sr.Attribute` with 6 samples / 192 B, and one
`BufferedInputStream` sample.

The key sampled stacks include `java.util.Arrays.copyOfRange` ->
`java.lang.String::<init>` -> `TextBuffer.contentsAsString` ->
`BasicStreamReader.getText` -> `WoodstoxBench.consume`, and
`TextBuilder.getAllValues` / `AttributeCollector.getValue` /
`BasicStreamReader.getAttributeValue`. This is a counterexample to any claim
that the current Woodstox comparator avoids Java string/char materialization
entirely while folding the checksum.

It is still not a deterministic allocation census and not a complete object
lifetime proof. The recording is process-level sampled JFR evidence and includes
JVM startup plus warmups because the comparator is launched as a separate
process. Use it to identify observed allocation paths, not to infer total
allocation volume or to prove the absence of other allocation paths.

`packages/benchmark/results/release/woodstox-measured-jfr-allocation.md` is the
narrower follow-up `TRACE_FACT` for the same Java/HotSpot build and 16 MiB
fixture. The Java comparator starts JFR after warmups and after the pre-run
`System.gc()`, then stops and dumps the recording immediately after the measured
`consume` call. This removes JVM startup and warmup allocation from the captured
JFR event window.

The measured-run JFR row also preserves the checksum contract: 967,967 events
and checksum `-746772258`. With JFR active only around the measured consume call,
the timed row reported 201.1 MiB/s, so this artifact should not replace the
non-JFR Woodstox throughput baseline. It is allocation-path evidence, not a
speed baseline.

JFR reported 10 `ObjectAllocationInNewTLAB` samples and zero
`ObjectAllocationOutsideTLAB` samples in the measured window. All 10 samples
were on the main thread, under `WoodstoxBench.consume`, and under Woodstox
stacks; 9 were string-boundary samples. The sampled classes were `char[]` with
5 samples / 336 B, `java.lang.String` with 4 samples / 96 B, and
`com.ctc.wstx.sr.Attribute` with 1 sample / 32 B. The observed stacks again
cross `TextBuffer.contentsAsString`, `TextBuilder.getAllValues`,
`AttributeCollector.getValue`, `BasicStreamReader.getText`, and
`BasicStreamReader.getAttributeValue`.

This strengthens the counterexample to "Woodstox avoids Java string/char
materialization entirely" because it no longer depends on startup or warmup
samples. It still remains sampled evidence, not a total allocation census or
proof of every object lifetime.

## Current Evidence: Rust quick-xml Shape Audit

`packages/benchmark/results/release/quick-xml-shape-audit.md` is a
`SOURCE_FACT` for the recorded source boundary: Rust comparator source in this
repository plus local `quick-xml` 0.40.1 crate source.

The current external baseline anchors the comparator to the same 16 MiB
full-string checksum contract: quick-xml reported 309.8 MiB/s, 967,967 events,
checksum `-746772258`, and 0.93x of the Woodstox row in
`packages/benchmark/results/release/external-baseline.md`.

The source audit records that the comparator uses `read_event_into(&mut
buffer)`, clears and reuses that buffer, folds element and attribute names from
byte views, decodes text/CDATA through `Cow<str>`, and folds UTF-16 code units
to match the JavaScript checksum. quick-xml source stores event data as
`Cow<[u8]>` and returns `Event<'b>` tied to the caller buffer lifetime. The
current comparator still materializes each start tag's attributes into a `Vec`
before folding because the checksum mixes attribute count before names/values.

This is strong evidence that quick-xml is not the same shape as a JavaScript
public event-object reader. It is not an allocation profile or machine-code
trace, and it does not prove how often `Cow<str>` is borrowed versus owned on
real inputs.

`packages/benchmark/results/release/quick-xml-allocation-count.md` is a
follow-up `TRACE_FACT` for the same Rust + quick-xml comparator binary and 16
MiB fixture. The comparator uses an opt-in Rust global allocator counter,
starts the counter after four warmup runs and immediately before the measured
`consume()` call, then stops it immediately after `consume()` returns.

The allocation-count row preserves the checksum contract: 967,967 events and
checksum `-746772258`. With allocator counting enabled, the timed row reported
282.7 MiB/s; this is an instrumented row and must not replace the
non-instrumented quick-xml throughput baseline. The measured window counted
170,822 allocation calls, 170,822 deallocation calls, 2 realloc calls, 170,824
allocation operations, 27.13 MiB total allocated bytes, and 0 B net allocated
bytes.

This turns the previous "allocation-still-missing" gap into a narrower fact:
quick-xml allocation calls are now counted for the measured comparator window,
but the counter still has no stack attribution, type attribution, object
lifetime proof, or borrowed-vs-owned `Cow<str>` frequency. It is therefore
allocation-call evidence, not proof that quick-xml's speed follows from one
specific representation choice.

## Current Evidence: Object-Shape Parity

`packages/benchmark/results/release/object-shape-parity.md` is a `BENCH_FACT`
only for its recorded boundary: Node/V8, one 16 MiB fixture, `warmups=1`, and
`runs=3`.

It compares five JavaScript rows under the same full-string checksum contract:

- `stream-batch-index`: `StreamBatch` index accessors, no per-event object;
- `stream-event-view`: `StreamEventView` wrapper per event;
- `cursor-adapter`: one mutable cursor over `StreamBatch`;
- `event-reader-object`: public `EventReaderSync` event objects;
- `raw-frame-name-id`: `nextRawBatch()` typed arrays with numeric name-id cache.

The measured throughputs were 124.2 MiB/s, 86.4 MiB/s, 107.5 MiB/s,
94.3 MiB/s, and 136.8 MiB/s respectively. All rows reported the same
967,967 events and checksum `-746772258`.

This is useful evidence against collapsing every gap into parser-core cost:
per-event wrapper/object rows were slower than batch index access under the same
checksum, and the raw-frame name-id row was faster than public shapes. It does
not prove a 200 MiB/s JavaScript runtime ceiling. No 200 MiB/s counterexample
was found in this run, but 1 GiB+ bounded-memory rows, browser runs, allocation
profiles, and current V8/JSC traces are still missing.

## Current Evidence: Monomorphic Materialization Counters

`packages/benchmark/results/release/monomorphic-batch-access.md` is a
`BENCH_FACT` for the recorded boundary: Node/V8, one 16 MiB fixture,
`warmups=1`, and `runs=3`.

It compares `public-accessor`, `raw-frame-direct-decode`, and
`raw-frame-name-id-cache` with the same event/checksum contract. Counters are
collected in a separate parity-checked pass after timed samples, so the
throughput rows are not measuring counter instrumentation overhead.

The measured throughputs were 107.5 MiB/s, 121.0 MiB/s, and 132.3 MiB/s
respectively. All rows reported 967,967 events, checksum `-746772258`, and
1,537,355 consumed string fields. The raw direct row materialized 1,537,355 raw
spans; the name-id cache row materialized 569,400 raw spans with 967,955 name
cache hits and 10 misses.

This narrows a concrete headroom source: repeated name materialization is
measurably reduced by the numeric name-id cache, but the best row still reaches
only 0.40x of the current Woodstox baseline and remains below the 0.9x target.
This is not a proof that no further JavaScript headroom exists.

## Current Evidence: V8 Monomorphic Shape Trace

`packages/benchmark/results/release/v8-monomorphic-shape-trace.md` is a
`TRACE_FACT` for the recorded boundary: Node `24.15.0`, V8
`13.6.233.17-node.48`, 128 generated elements, `warmups=24`, and
`iterations=6`.

It traces the same three monomorphic JavaScript rows as the 16 MiB benchmark:

- `public-accessor`;
- `raw-frame-direct-decode`;
- `raw-frame-name-id-cache`.

All rows reported the same 2,180 events and checksum `1331061553`. V8 reported
TurboFan optimization with zero post-warmup deopts for all three rows in this
quick trace. The filtered optimized-code logs still showed native/runtime/deopt
signals: `public-accessor` had `CEntry=22`, `TypedArrayPrototypeSubArray=1`,
and `DeoptExit=432`; `raw-frame-direct-decode` had `CEntry=45`,
`TypedArrayPrototypeSubArray=8`, and `DeoptExit=988`; `raw-frame-name-id-cache`
had `CEntry=25`, `TypedArrayPrototypeSubArray=4`, and `DeoptExit=528`.

This narrows the current explanation: the raw-frame/name-id rows are not merely
waiting on obvious post-warmup V8 deopt removal in this small run. It does not
prove that V8 has no codegen headroom, does not replace allocation sampling, and
does not cover Bun/JSC or browser engines.

## Current Evidence: V8 Allocation Sampling

`packages/benchmark/results/release/v8-allocation-sampling.md` is a
`TRACE_FACT` for the recorded boundary: Node `24.15.0`, V8
`13.6.233.17-node.48`, the 16 MiB runtime-comparison fixture, `warmups=1`,
`iterations=4`, and a 2 KiB HeapProfiler sampling interval.

It samples the public event-object row plus the three monomorphic JavaScript
rows used by the materialization counter benchmark and the V8 codegen trace:

- `public-accessor`;
- `event-reader-object`;
- `raw-frame-direct-decode`;
- `raw-frame-name-id-cache`.

All sampled rows reported 967,967 events and checksum `-746772258`. The sampled
allocation totals were 238.4 KiB, 79.3 KiB, 81.5 KiB, and 97.4 KiB
respectively. The sampled `stax-xml` source bytes were 74.3 KiB, 65.1 KiB,
49.1 KiB, and 55.6 KiB respectively. The sample counts were 88, 25, 27, and 31
respectively.

This supports the current implementation-headroom explanation: public accessors
and raw-frame rows differ not only in timing but also in sampled JavaScript
allocation shape under the same checksum contract. The public event-object row
is now sampled under the same contract with a smaller sampling interval, but
function/source byte attribution is still sampled self-size only. This does not
prove that V8 has no allocation headroom, does not cover Bun/JSC or browsers,
and does not prove a JavaScript runtime ceiling.

`packages/benchmark/results/release/v8-allocation-sampling-diverse.md` is a
second `TRACE_FACT` for the same Node/V8 build with a less-repetitive generated
16 MiB fixture, `warmups=1`, `iterations=4`, and a 2 KiB HeapProfiler sampling
interval. The generated fixture varies element names, attribute names, attribute
values, text values, and includes periodic non-ASCII text.

All diverse-fixture sampled rows reported 662,215 events and checksum
`-2075823699`. The sampled allocation totals were 248.3 KiB, 71.6 KiB,
68.2 KiB, and 76.0 KiB for `public-accessor`, `event-reader-object`,
`raw-frame-direct-decode`, and `raw-frame-name-id-cache` respectively. The
sample counts were 94, 21, 22, and 23 respectively; the public event-object row
therefore no longer rests on the two-sample evidence from the first report.
The measured average times were 222.81 ms, 417.58 ms, 244.60 ms, and
211.86 ms respectively.

This reduces one sampling weakness in the public event-object evidence and adds
a less-repetitive fixture countercheck. It still remains statistical
HeapProfiler evidence for a 16 MiB string-input fixture. It does not cover
1 GiB bounded-memory rows, Bun/JSC, browser engines, or a deterministic
allocation census, and it still does not prove a JavaScript runtime ceiling.

## Current Evidence: 1 GiB Generated Byte-Batch Shape

`packages/benchmark/results/release/stream-reader-1gb-shapes.md` is a
`BENCH_FACT` only for its recorded boundary: Node `24.15.0`, V8
`13.6.233.17-node.48`, generated repeated `<person>` rows, `warmups=0`, and
`runs=1`.

It uses `StreamReaderSync` over generated `Uint8Array` batches, so it does not
load a complete 1 GiB XML document string. The compared rows are:

- `index-for`: public `StreamBatch` index accessors;
- `raw-frame-direct`: `nextRawBatch()` typed arrays with direct span
  materialization;
- `raw-frame-name-id`: `nextRawBatch()` typed arrays with numeric name-id cache.

The measured throughputs were 94.60 MiB/s, 87.31 MiB/s, and 98.45 MiB/s
respectively. All rows reported 143,165,586 events, checksum `-1871242243`,
and 178,956,980 consumed string fields. Max RSS endpoints stayed between
58.5 MiB and 64.3 MiB.

This is evidence that the current generated byte-batch reader shape can keep
memory bounded while consuming 1 GiB+ input. It is not a global runtime-limit
proof: the fixture is intentionally simple and repetitive, the run count is one,
browser rows are absent, and V8/JSC allocation/codegen evidence is still
missing. No 200 MiB/s counterexample was found in this bounded-memory run.

`packages/benchmark/results/release/stream-reader-1gb-allocation-shapes.md` is
a `BENCH_FACT` plus `TRACE_FACT` for the same generated byte-batch shape with
V8 HeapProfiler allocation sampling enabled. It uses a 1 GiB generated repeated
`<person>` fixture, `warmups=0`, `runs=1`, and an 8 KiB sampling interval. The
raw heapprofile artifacts are intentionally not committed.

The allocation-sampling run reported 143,165,586 events and checksum
`-1871242243` for all rows. Throughputs were 86.42 MiB/s for `index-for`,
75.14 MiB/s for `raw-frame-direct`, and 89.60 MiB/s for
`raw-frame-name-id`. Max RSS endpoints were 59.8 MiB, 60.2 MiB, and
65.3 MiB respectively. Sampled allocation bytes were 171.7 KiB, 121.3 KiB,
and 99.6 KiB with sample counts 19, 13, and 11 respectively.

This closes the narrow gap that the 1 GiB byte-batch shape had no V8 allocation
sampling at all. It still does not prove a runtime ceiling: the fixture is
repetitive, the run count is one, the sampling is statistical self-size
evidence, and this does not cover string-input public event objects, Bun/JSC, or
browser engines.

`packages/benchmark/results/release/stream-reader-1gb-diverse-shapes.md` is a
`BENCH_FACT` for the same bounded-memory byte-batch path without V8
HeapProfiler allocation sampling overhead. It uses a 4,096-row deterministic
`diverse-cycle` fixture, `warmups=0`, and `runs=3`.

The no-profiler diverse-cycle run reported 45,189,256 events and checksum
`1421012805` for all rows. Throughputs were 96.08 MiB/s for `index-for`,
80.70 MiB/s for `raw-frame-direct`, and 95.31 MiB/s for `raw-frame-name-id`.
Average RSS deltas were 3.0 MiB, 3.6 MiB, and 744.0 KiB respectively, and max
RSS endpoints were 67.9 MiB, 77.3 MiB, and 79.1 MiB.

This separates throughput/RSS variability from HeapProfiler overhead for the
less-repetitive 1 GiB generated fixture. It is stronger than the allocation
sample for timing claims, but it is not an allocation profile, not a browser or
Bun/JSC result, and not proof that no further JavaScript implementation
headroom exists.

`packages/benchmark/results/release/stream-reader-1gb-allocation-diverse-shapes.md`
is a 1 GiB generated byte-batch `BENCH_FACT` plus `TRACE_FACT`. It uses the same
bounded-memory byte-batch path and the same 4,096-row deterministic
`diverse-cycle` fixture as the no-profiler run, but enables V8 HeapProfiler
allocation sampling with an 8 KiB interval. The row cycle varies element names,
attribute names, attribute values, text values, and periodic non-ASCII text. It
does not load a complete XML document string.

The diverse-cycle run reported 45,189,256 events and checksum `1421012805` for
all rows. Throughputs were 94.11 MiB/s for `index-for`, 69.64 MiB/s for
`raw-frame-direct`, and 84.42 MiB/s for `raw-frame-name-id`. Max RSS endpoints
were 67.6 MiB, 67.5 MiB, and 68.1 MiB respectively. Sampled allocation bytes
were 249.8 KiB, 115.0 KiB, and 101.1 KiB with sample counts 28, 13, and 12
respectively.

This is a concrete countercheck against relying only on the single-row 1 GiB
fixture. It still does not prove a runtime ceiling: the diverse rows repeat as a
finite cycle, the run count is one, and the evidence remains Node/V8 statistical
self-size sampling rather than browser/JSC/Bun coverage or a deterministic
allocation census.

## Required Proof Tracks

### Track A: Comparator Shape Proof

Goal: prove what each runtime comparator actually materializes.

Evidence to gather:

- Woodstox HotSpot `PrintCompilation` and `PrintInlining`.
- JFR or async-profiler allocation profile for `WoodstoxBench.consume`.
- If available, hsdis/JITWatch assembly for hot `XMLStreamReader` accessors.
- quick-xml symbol/asm profile narrowed to reader, name decode, text decode,
  and attribute decode paths.
- JS rows split into `stax-stream`, `stax-event`, raw frame, and any cursor-like
  shape under the same fixture and checksum.

Acceptance:

- The report must distinguish cursor/accessor calls, public event objects,
  attribute objects/maps, strings returned by accessors, and borrowed/owned
  string views.

### Track B: JavaScript Runtime Proof

Goal: separate language/runtime invariants from implementation headroom.

Evidence to gather:

- Pinned V8 source references for the exact Node/V8 release used in benchmark
  reports.
- Pinned JavaScriptCore source references for the exact Bun/JSC release when
  possible.
- V8 optimized-code and allocation evidence for public accessor, raw-frame
  direct, name-id cache, and public event object rows.
- Bun/JSC codegen evidence for the same rows.
- Browser harness results for Chrome and at least one non-V8 browser when the
  browser claim is made.

Acceptance:

- A language-limit conclusion requires both source-level invariants and
  negative benchmark/profiler evidence across the serious implementation
  shapes. Source facts alone can only prove string lifetime/copy boundaries.

### Track C: Candidate Headroom Matrix

Goal: find counterexamples before claiming limits.

Minimum rows:

- `scanAllNoDecode`
- `nameStringOnly`
- `textStringOnly`
- `attrNameStringOnly`
- `attrValueStringOnly`
- `stringFull`
- `eventObjectFull`

  using Node-only APIs is not a counterexample for the neutral StAX API claim.
