# stax-api Performance Proof Ledger

Status: active proof ledger
Date: 2026-05-23

## Purpose

This ledger prevents performance work from mixing three different claims:

- what the current `stax-xml` implementation has measured;
- what V8, JavaScriptCore, HotSpot, Woodstox, and quick-xml source evidence can
  prove;
- what remains an optimization hypothesis with possible counterexamples.

The target remains a StAX-like JavaScript reader that gives the best possible
throughput with bounded memory on large XML inputs in Node and browser
JavaScript runtimes. This document does not conclude that JavaScript runtimes
cannot exceed 200 MiB/s for the target shape. That conclusion is explicitly not
proved.

## Proof Vocabulary

| Term | Meaning | May support a final conclusion? |
| --- | --- | --- |
| `SOURCE_FACT` | Direct fact from current repository or upstream source code. | Yes, for code shape only. |
| `TRACE_FACT` | Generated bytecode, JIT, asm, profiler, or allocation evidence from a specific runtime/build. | Yes, but only for that runtime/build/input. |
| `BENCH_FACT` | Reproducible benchmark result with fixture, command, parity, memory, and environment recorded. | Yes, for that benchmark boundary. |
| `ENGINE_INVARIANT` | Runtime/language property backed by source or spec, such as engine-owned JS string storage. | Yes, but only for the exact invariant. |
| `NEGATIVE_RESULT` | A tried implementation line that failed under recorded gates. | No global conclusion; it narrows search space. |
| `COUNTEREXAMPLE` | Evidence that disproves a claim or forces a weaker claim. | Yes, to reject that claim. |
| `HYPOTHESIS` | Plausible explanation or direction that is not proven. | No. |
| `CONCLUSION` | Claim allowed in release docs only after all proof obligations are met. | Yes. |

Rules:

- A `CONCLUSION` must list its accepted evidence and known counterexample
  searches.
- `ENGINE_INVARIANT` about JS strings is not by itself a performance
  impossibility proof.
- `NEGATIVE_RESULT` for lazy getters, Buffer lanes, or value caches does not
  prove that all JavaScript runtime headroom is exhausted.
- Projection/selectivity wins do not prove full-materialization StAX wins.
- `byteFull` is an upper bound only when it avoids string materialization.
  `stringFull` remains the realistic parity metric for string-return claims.

## Current Evidence: Object-Shape Parity

`packages/benchmark/results/release/object-shape-parity.md` is a `BENCH_FACT`
only for its recorded boundary: Node/V8, one 16 MiB fixture, `warmups=1`, and
`runs=3`.

It compares five JavaScript rows under the same full-string checksum contract:

- `stream-batch-index`: `StreamBatch` index accessors, no per-event object;
- `stream-event-view`: `StreamEventView` wrapper per event;
- `cursor-adapter`: one mutable cursor over `StreamBatch`;
- `event-reader-object`: public `EventReaderSync` event objects;
- `raw-frame-name-id`: `nextRawBatch()` typed arrays with numeric name-id cache.

The measured throughputs were 124.2 MiB/s, 86.4 MiB/s, 107.5 MiB/s,
94.3 MiB/s, and 136.8 MiB/s respectively. All rows reported the same
967,967 events and checksum `-746772258`.

This is useful evidence against collapsing every gap into parser-core cost:
per-event wrapper/object rows were slower than batch index access under the same
checksum, and the raw-frame name-id row was faster than public shapes. It does
not prove a 200 MiB/s JavaScript runtime ceiling. No 200 MiB/s counterexample
was found in this run, but 1 GiB+ bounded-memory rows, browser runs, allocation
profiles, and current V8/JSC traces are still missing.

## Current Evidence: 1 GiB Generated Byte-Batch Shape

`packages/benchmark/results/release/stream-reader-1gb-shapes.md` is a
`BENCH_FACT` only for its recorded boundary: Node `24.15.0`, V8
`13.6.233.17-node.48`, generated repeated `<person>` rows, `warmups=0`, and
`runs=1`.

It uses `StreamReaderSync` over generated `Uint8Array` batches, so it does not
load a complete 1 GiB XML document string. The compared rows are:

- `index-for`: public `StreamBatch` index accessors;
- `raw-frame-direct`: `nextRawBatch()` typed arrays with direct span
  materialization;
- `raw-frame-name-id`: `nextRawBatch()` typed arrays with numeric name-id cache.

The measured throughputs were 94.60 MiB/s, 87.31 MiB/s, and 98.45 MiB/s
respectively. All rows reported 143,165,586 events, checksum `-1871242243`,
and 178,956,980 consumed string fields. Max RSS endpoints stayed between
58.5 MiB and 64.3 MiB.

This is evidence that the current generated byte-batch reader shape can keep
memory bounded while consuming 1 GiB+ input. It is not a global runtime-limit
proof: the fixture is intentionally simple and repetitive, the run count is one,
browser rows are absent, and V8/JSC allocation/codegen evidence is still
missing. No 200 MiB/s counterexample was found in this bounded-memory run.

## Required Proof Tracks

### Track A: Comparator Shape Proof

Goal: prove what each runtime comparator actually materializes.

Evidence to gather:

- Woodstox HotSpot `PrintCompilation` and `PrintInlining`.
- JFR or async-profiler allocation profile for `WoodstoxBench.consume`.
- If available, hsdis/JITWatch assembly for hot `XMLStreamReader` accessors.
- quick-xml symbol/asm profile narrowed to reader, name decode, text decode,
  and attribute decode paths.
- JS rows split into `stax-stream`, `stax-event`, raw frame, and any cursor-like
  shape under the same fixture and checksum.

Acceptance:

- The report must distinguish cursor/accessor calls, public event objects,
  attribute objects/maps, strings returned by accessors, and borrowed/owned
  string views.

### Track B: JavaScript Runtime Proof

Goal: separate language/runtime invariants from implementation headroom.

Evidence to gather:

- Pinned V8 source references for the exact Node/V8 release used in benchmark
  reports.
- Pinned JavaScriptCore source references for the exact Bun/JSC release when
  possible.
- V8 optimized-code and allocation evidence for public accessor, raw-frame
  direct, name-id cache, and public event object rows.
- Bun/JSC codegen evidence for the same rows.
- Browser harness results for Chrome and at least one non-V8 browser when the
  browser claim is made.

Acceptance:

- A language-limit conclusion requires both source-level invariants and
  negative benchmark/profiler evidence across the serious implementation
  shapes. Source facts alone can only prove string lifetime/copy boundaries.

### Track C: Candidate Headroom Matrix

Goal: find counterexamples before claiming limits.

Minimum rows:

- `scanAllNoDecode`
- `nameStringOnly`
- `textStringOnly`
- `attrNameStringOnly`
- `attrValueStringOnly`
- `stringFull`
- `eventObjectFull`
- `rawFrameDirect`
- `rawFrameNameId`
- `cursorAccessor`
- `projectionLowSelectivity`
- `projectionHighSelectivity`

Minimum evidence columns:

- throughput MiB/s;
- event count and checksum/parity status;
- materialized string count if measurable;
- event/object count if measurable;
- heap delta, RSS delta, and max RSS;
- GC time share where available;
- runtime and engine versions.

Acceptance:

- A candidate that reaches 200 MiB/s+ with bounded memory on 1 GiB+ input is a
  counterexample to `CLAIM-JS-RUNTIME-LIMIT-200MIB`.
- A candidate that only wins by dropping strings, changing event semantics, or
  using Node-only APIs is not a counterexample for the neutral StAX API claim.
