# stax-api Performance Proof Ledger

Status: active proof ledger
Date: 2026-05-23

## Purpose

This ledger prevents performance work from mixing three different claims:

- what the current `stax-xml` implementation has measured;
- what V8, JavaScriptCore, HotSpot, Woodstox, and quick-xml source evidence can
  prove;
- what remains an optimization hypothesis with possible counterexamples.

The target remains a StAX-like JavaScript reader that gives the best possible
throughput with bounded memory on large XML inputs in Node and browser
JavaScript runtimes. This document does not conclude that JavaScript runtimes
cannot exceed 200 MiB/s for the target shape. That conclusion is explicitly not
proved.

## Proof Vocabulary

| Term | Meaning | May support a final conclusion? |
| --- | --- | --- |
| `SOURCE_FACT` | Direct fact from current repository or upstream source code. | Yes, for code shape only. |
| `TRACE_FACT` | Generated bytecode, JIT, asm, profiler, or allocation evidence from a specific runtime/build. | Yes, but only for that runtime/build/input. |
| `BENCH_FACT` | Reproducible benchmark result with fixture, command, parity, memory, and environment recorded. | Yes, for that benchmark boundary. |
| `ENGINE_INVARIANT` | Runtime/language property backed by source or spec, such as engine-owned JS string storage. | Yes, but only for the exact invariant. |
| `NEGATIVE_RESULT` | A tried implementation line that failed under recorded gates. | No global conclusion; it narrows search space. |
| `COUNTEREXAMPLE` | Evidence that disproves a claim or forces a weaker claim. | Yes, to reject that claim. |
| `HYPOTHESIS` | Plausible explanation or direction that is not proven. | No. |
| `CONCLUSION` | Claim allowed in release docs only after all proof obligations are met. | Yes. |

Rules:

- A `CONCLUSION` must list its accepted evidence and known counterexample
  searches.
- `ENGINE_INVARIANT` about JS strings is not by itself a performance
  impossibility proof.
- `NEGATIVE_RESULT` for lazy getters, Buffer lanes, or value caches does not
  prove that all JavaScript runtime headroom is exhausted.
- Projection/selectivity wins do not prove full-materialization StAX wins.
- `byteFull` is an upper bound only when it avoids string materialization.
  `stringFull` remains the realistic parity metric for string-return claims.

## Runtime-Limit Conclusion Gate

`CLAIM-JS-RUNTIME-LIMIT-200MIB` may not move from `HYPOTHESIS` to
`CONCLUSION` merely because current full-string benchmark rows are slow. The
claim needs a proof bundle that separates static runtime invariants from failed
counterexample searches.

Required proof obligations:

- Define the target shape as a full-string StAX-like reader contract, not as
  identical object shape across languages. Woodstox and quick-xml remain
  comparator rows through semantic fields, event count, and checksum parity,
  not through JavaScript object-shape parity.
- List every serious JavaScript counterexample family tested: public event
  objects, stream/index accessors, raw frame direct decode, raw frame name-id
  cache, cursor-like accessors, TextDecoder span variants, complete-string
  references, projection rows as separated non-StAX headroom evidence, and any
  runtime-specific optional lanes.
- Pin source facts for the exact runtime builds used in the benchmark claim:
  string primitive ownership, ordinary string creation/copy boundaries,
  TextDecoder/span-view behavior where source evidence is available, and
  maximum string-size boundaries where complete-string input is discussed.
- Pair source facts with runtime evidence: JIT/codegen/profiler/allocation
  captures for the relevant implementation shapes on each claimed engine.
- Require 1 GiB+ same-contract benchmark rows with memory gates across enough
  fixtures and runtimes to make the claim scope explicit. A single engine, a
  single generated cycle, or a single negative micro-variant is not sufficient.
- Treat any 200 MiB/s+ bounded-memory full-string JavaScript row as a
  counterexample. Treat partial byte-scan, projection, and Node-only rows as
  narrower headroom evidence unless they preserve the full StAX contract.

Current allowed statement: the present artifacts have not found a
200 MiB/s+ bounded-memory full-string JavaScript counterexample. They do not
prove that JavaScript runtimes have no further headroom.

## Current Evidence: 1 GiB Corpus-Cycle Candidate Headroom Matrix

`packages/benchmark/results/release/candidate-headroom-corpus.md` and
`packages/benchmark/results/release/bun-candidate-headroom-corpus.md` are
`BENCH_FACT` rows for a less synthetic 1 GiB+ byte-batch counterexample search.
Both artifacts repeat the existing
`packages/stax-xml/performance/samples/treebank_e.xml` corpus seed as
`corpus-cycle` byte batches. The seed is 89,565,617 bytes; the emitted input is
1,074,787,404 bytes. The benchmark now defaults corpus-cycle batch size to `1`
so the harness does not accidentally materialize a 1 GiB batch from an
85.4 MiB seed. Both Node/V8 and Bun/JSC artifacts record their GC strategy:
`globalThis.gc` for Node and `Bun.gc` for Bun.

This fixture is structurally different from the generated `diverse-cycle`
rows. It is mostly nested treebank-like tags and text, with only 12 attribute
pairs across the repeated corpus cycle. That makes it a useful countercheck for
name/text-heavy XML, but not a broad real-world corpus suite.

Node/V8 partial rows did not exceed 200 MiB/s in the regenerated artifact:
`scanAllNoDecode` reported `138.76 MiB/s`, `attrNameStringOnly` reported
`108.28 MiB/s`, and `attrValueStringOnly` reported `108.78 MiB/s`, all below
the 512 MiB RSS gate. The full-string parity rows reported `62.17 MiB/s` for
`stringFull`, `61.80 MiB/s` for `eventObjectFull`, `66.95 MiB/s` for
`cursorAccessor`, `71.51 MiB/s` for `rawFrameDirect`, and `rawFrameNameId` at
`77.00 MiB/s`. All full rows reported 75,206,126 events and checksum
`-925527041`; `eventObjectFull` counted 75,206,126 public event objects, and
`rawFrameNameId` materialized 16,702,403 raw spans with 58,503,745 name-cache
hits and 251 misses.

Bun/JSC partial rows also did not exceed 200 MiB/s: `scanAllNoDecode` reported
`177.78 MiB/s`, `nameStringOnly` reported `107.41 MiB/s`,
`attrNameStringOnly` reported `115.99 MiB/s`, and `attrValueStringOnly`
reported `112.42 MiB/s`. The fastest full parity row was `rawFrameNameId` at
`76.08 MiB/s`, with the same 75,206,126 events and checksum `-925527041`;
`eventObjectFull` reported `62.08 MiB/s`. Bun/JSC corpus-cycle rows were not
bounded under the 512 MiB RSS gate: their max RSS endpoints ranged from
557.6 MiB to 1.71 GiB.

No full-string 200 MiB/s counterexample was found on this corpus-cycle input.
The result is still not a JavaScript runtime ceiling proof: the corpus is one
seed repeated to 1 GiB, both rows use `runs=1`, browser engines are absent, and
Bun/JSC needs isolated or lower-retention memory investigation before its
corpus memory profile can be considered acceptable.

`packages/benchmark/results/release/stream-reader-1gb-diverse-shapes.md` is a

`packages/benchmark/results/release/stream-reader-1gb-allocation-diverse-shapes.md`

## Required Proof Tracks

### Track A: Comparator Shape Proof

Goal: prove what each runtime comparator actually materializes.

Evidence to gather:

- Woodstox HotSpot `PrintCompilation` and `PrintInlining`.
- JFR or async-profiler allocation profile for `WoodstoxBench.consume`.
- If available, hsdis/JITWatch assembly for hot `XMLStreamReader` accessors.
- quick-xml symbol/asm profile narrowed to reader, name decode, text decode,
  and attribute decode paths.
- JS rows split into `stax-stream`, `stax-event`, raw frame, and any cursor-like
  shape under the same fixture and checksum.

Acceptance:

- The report must distinguish cursor/accessor calls, public event objects,
  attribute objects/maps, strings returned by accessors, and borrowed/owned
  string views.

### Track B: JavaScript Runtime Proof

Goal: separate language/runtime invariants from implementation headroom.

Evidence to gather:

- Pinned V8 source references for the exact Node/V8 release used in benchmark
  reports.
- Pinned JavaScriptCore source references for the exact Bun/JSC release are now
  present; exact Safari/browser JSC pins remain separate if Safari rows are
  claimed.
- V8 optimized-code and allocation evidence for public accessor, raw-frame
  direct, name-id cache, and public event object rows.
- Bun/JSC profiler evidence is now present for selected rows; codegen/IR
  evidence for the same rows remains open.
- Browser harness results for Chrome and at least one non-V8 browser when the
  browser claim is made; the current Chrome and Firefox generated byte-batch
  rows are still narrow browser points and do not cover portable process RSS.
- The Firefox/Gecko TextDecoder source boundary is now pinned for the installed
  Firefox 143.0.1 SourceStamp and Firefox generated benchmark rows now exist,
  but SpiderMonkey codegen traces and allocation evidence remain open.

Acceptance:

- A language-limit conclusion requires both source-level invariants and
  negative benchmark/profiler evidence across the serious implementation
  shapes. Source facts alone can only prove string lifetime/copy boundaries.

### Track C: Candidate Headroom Matrix

Goal: find counterexamples before claiming limits.

Minimum rows:

- `scanAllNoDecode`
- `nameStringOnly`
- `textStringOnly`
- `attrNameStringOnly`
- `attrValueStringOnly`
- `stringFull`
- `eventObjectFull`
- `rawFrameDirect`
- `rawFrameNameId`
- `cursorAccessor`
- TextDecoder span variants (`subarraySharedDecoder`, `viewSharedDecoder`,
  `sliceCopySharedDecoder`, `subarrayNewDecoder`, and a clearly marked
  short-ASCII diagnostic row)
- `projectionLowSelectivity`
- `projectionHighSelectivity`

Minimum evidence columns:

- throughput MiB/s;
- event count and checksum/parity status;
- materialized string count if measurable;
- event/object count if measurable;
- heap delta, RSS delta, and max RSS;
- GC time share where available;
- runtime and engine versions.

Acceptance:

- A full-string parity candidate that reaches 200 MiB/s+ with bounded memory on
  1 GiB+ input is a counterexample to `CLAIM-JS-RUNTIME-LIMIT-200MIB`.
- A candidate that only wins by dropping strings, changing event semantics, or
  using Node-only APIs is not a counterexample for the neutral StAX API claim,
  but it is still headroom evidence for the narrower runtime/parser boundary.
