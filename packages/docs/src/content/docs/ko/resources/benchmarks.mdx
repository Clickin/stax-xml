<summary>Scenario contract: Node parser library 비교</summary>

Sample XML shape, 축약:

~~~xml
<catalog>
  <book id="..." category="...">
    <title>...</title>
    <author>...</author>
    <price currency="USD">...</price>
    <tags><tag>...</tag></tags>
  </book>

~~~

Consumer/output shape, 라이브러리 중립 pseudo code:

~~~text
consume-only:
  for each parser event:
    event를 count 또는 inspect
    전체 output tree는 보관하지 않음

object-output:
  document = {
    catalog: {
      book: [
        { attributes, title, author, price, tags }
      ]
    }
  }
~~~

런타임별 파싱 방법:

API 선택 기준:

- 목표 XML-to-object shape를 알고 있다면 converter API를 우선 사용합니다.
- 전체 XML 순회가 필요하고 per-event 작업이 가볍다면 `EventReader` 또는 `EventReaderSync`를 먼저 시도합니다.
- unknown-schema projection이나 object materialization이 무겁다면 `ProjectionReader`와 `stax-xml/projection` helper를 사용합니다.
- converter가 XPath 1.0 selector와 field transform을 목표로 하기 때문에, selector 중심의 대부분의 `if` 분기는 predicate, position, descendant path, attribute test 같은 선언형 schema로 옮길 수 있습니다.
- 반대로 stream 순서, 조기 종료, side effect, mutable cross-record state처럼 XPath selection으로 표현되지 않는 로직은 `EventReader` 또는 `StreamReader`에 남겨야 합니다.

- `stax-xml StreamReaderSync (native)`: `initStaxXml({ backend: "native" })`와 native streaming runtime으로 구동되는 public lean byte-batch pull reader입니다. headline native wrapper claim은 이 row가 direct native addon full-spec file-input control row의 `0.90x` 이상일 때만 허용합니다. 이 floor에 못 미치는 결과는 row 삭제나 final spec 하향의 이유가 아니라 public surface를 끌어올리기 위한 최적화 evidence로 남깁니다.
- `stax-xml EventReaderSync (native reference)`: native runtime으로 구동되는 ergonomic string event iterator입니다. object/iterator overhead를 추적하는 reference row로 계속 측정하지만, 0.9x gate 대상은 아닙니다.
- `stax-xml ProjectionReader parseXmlNodes (native)`: `stax-xml/projection`을 통해 txml-style node를 반환하는 public unknown-schema object projection입니다.
- `stax-xml to object`: object-shape reference row입니다. object materialization의 public 성능 근거는 native `ProjectionReader` row를 기준으로 봅니다.
- `txml`, `fast-xml-parser`, `xml2js`: 각 라이브러리의 native object/DOM-style parse API를 사용합니다.
- 이 parser fixture 시리즈는 third-party parser가 아니라 public stax-xml surface끼리 비교합니다.
- 모든 행은 fixture마다 같은 최종 JavaScript object array를 만든 뒤 반환합니다.
- `EventReaderSync`: native-backed public string event iterator + manual object builder
- `StreamReaderSync`: native-backed public byte-stream pull reader + manual object builder
- `ProjectionReader`: 같은 object shape를 반환하는 native-backed public object-record projection
- `Converter`: 한 번 compile한 public declarative schema가 `schema.parseSync()`를 통해 같은 object shape를 반환합니다
- fixture input은 bytes로 메모리에 올리고, `EventReaderSync`는 decode된 string도 함께 받습니다. 즉 이 표는 low-memory large-file traversal benchmark가 아니라 in-memory sync 비교입니다.
- parser table의 memory column은 benchmark 호출의 Mitata average heap footprint입니다. bounded-reader peak RSS metric이 아닙니다.

- stax-xml 행은 local reference row이며 package-supported reader surface만 사용합니다. 이전 결과 데이터의 legacy internal byte-reader label은 benchmark label이지 public import 권장사항이 아닙니다.

### EventReader Stream Traversal (기본 1MiB ~ 1GiB)

bounded file chunk 위에서 stax-xml native traversal을 비교합니다:

<details>
<summary>Scenario contract: EventReader stream native file traversal</summary>

Generated XML shape, 축약:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<root>
  <book id="book-N">
    <title>Sample Book Title Number N ...</title>
    <author>Author Name N</author>
    <description>...</description>
    <chapters>
      <chapter number="1">...</chapter>
    </chapters>
  </book>
</root>
~~~

Consumer/output shape:

~~~text
parse-result = {
  events: number,
  checksum: structural fold(event type, element/text/attribute span lengths and boundary bytes)
}
~~~

파싱 방법:

- 이 섹션의 모든 row는 bounded temp-file chunk 위에서 public `EventReader` stream API를 사용합니다.
- `EventReader stream native`는 native backend로 package를 초기화한 뒤 같은 stream reader API를 측정합니다.
- XML tokenization은 CPU-intensive 작업입니다. async file read를 사용해도 parse loop 자체가 non-blocking이 되지는 않으므로, latency-sensitive main event loop thread에서 실행해야 한다면 Worker 또는 worker thread로 offload할지 결정하세요.
- 이 row들은 full object tree를 만들지 않고 structural checksum을 사용하므로 stream tokenization과 event materialization 비용을 측정합니다.
- 렌더링된 표의 memory column은 traversal run의 peak JS heap입니다. peak RSS는 raw JSON에 기록되며, 의미 있게 유지하려면 isolated process에서 측정해야 합니다.

</details>

기본 release set은 1GiB에서 멈춥니다. 4GiB traversal은 `release:update -- --include-stress`로 opt-in 실행할 수 있습니다.

<BenchmarkSection locale="ko" section="async-size" />

**주요 인사이트:**
- 이 섹션은 full-object materialization benchmark가 아니라 public stream reader throughput view입니다.
- row는 bounded file chunk 위에서 public native-backed `EventReader` stream API를 사용합니다.
- async stream parsing도 각 CPU parse batch가 실행되는 동안 main event loop를 block할 수 있습니다. visible latency가 중요하면 Worker 또는 worker thread를 사용하세요.
- 100MiB를 넘는 파일에서 전체 XML string을 보관할 수 없다면 public full-string sync path를 피하고 bounded input buffering을 위해 async stream을 사용하세요.

## 타 런타임 비교

아래 표는 동일한 event count와 checksum 계약에서 `stax-xml` JS on Node, package reader surface를 통해 측정한 `stax-xml` native runtime, Woodstox, `quick-xml`을 비교합니다.
Woodstox는 Java 8이 minimum runtime이므로 공개 기준은 Java 8입니다. Java 25는 JVM 버전 차이가 결론을 바꾸는지 확인하기 위해 별도로 측정합니다.

<details>
<summary>Scenario contract: stax-xml JS/native reader, Woodstox, quick-xml 비교</summary>

Sample XML shape은 runtime matrix와 같은 16 MiB 생성 `<root><book>...</book></root>` fixture입니다.

Output shape:

~~~text
comparator-result = {
  tier: "count-only" | "name-string-only" | "attr-value-string-only" | "text-string-only" | "full-string",
  implementation: "stax-xml-js-node" | "stax-xml-native-reader" | "woodstox-java8" | "quick-xml",
  eventCount: number,
  checksum: fold(selected event data for tier)
}
~~~

파싱 방법:

- `stax-xml JS on Node`: built JavaScript iterable backend를 Node에서 실행하고 tier별 checksum folding을 수행합니다.
- `stax-xml native reader`: `initStaxXml({ backend: "native" })`로 초기화한 뒤 supported package reader path를 in-memory bytes 위에서 측정합니다.
- Woodstox: Java StAX `XMLStreamReader`, namespace-aware parsing disabled, coalescing enabled, DTD/external entities disabled, buffered file input입니다.
- `quick-xml`: Rust `Reader` over buffered file input입니다. declaration, PI, doctype, comment는 skip하고, text는 checksum parity를 위해 trim합니다.
- Java 8은 Woodstox의 minimum runtime target이므로 public Woodstox row로 사용하고, Java 25는 별도 verification row입니다.

</details>

### 왜 native runtime acceleration이 성능 경로인가

pure JavaScript 경로는 내부/reference implementation으로 유지하지만, 더 이상 release 성능 상한으로 보지는 않습니다.
이번 release 전까지의 parser 작업에서는 V8에 맞춘 JavaScript loop shape가 iterable backend를 개선할 수는 있었지만, full-string workload에서는 특히 `quick-xml` 같은 native parser baseline을 충분히 따라잡지 못했습니다.
남은 주요 비용은 delimiter scanning, string materialization, attribute/text 주변의 안정적인 object/API shape입니다.

Rust native runtime package는 native tokenizer와 SIMD-oriented scanning 전략을 사용할 수 있는 경로입니다. 방향성은 `quick-xml`이나 simdjson류 native/vectorized parser와 더 가깝습니다.
Published benchmark row는 이제 direct native diagnostic entry point가 아니라 public reader surface를 통해 이 경로를 측정합니다. 따라서 package topology는 `stax-xml` facade를 유지하면서 optional native/Wasm acceleration package를 추가하고, binary를 로드할 수 없거나 원하지 않는 환경은 silent JavaScript fallback이 아니라 Wasm compatibility backend를 명시적으로 선택해야 합니다.

## Converter API vs Plain Parser

아래 벤치마크는 일반 converter object-output 경로와 projection 가능한
byte-input fast path를 함께 비교합니다.

- `EventReaderSync` 위에 직접 작성한 plain parser
- automatic dispatch-plan routing이 적용되는 선언형 converter API
- `.compile()`을 적용한 converter API
- compiled converter API가 `Buffer` 입력과 projection 가능한 schema를 만나
  public native `stax-xml/projection` surface로 낮아지는 경로
- converter object hydration 없이 native columnar row projection을 반환하는
  `ProjectionReader` 자체 경로

권장 방향: 이처럼 목표 object shape가 알려진 경우 ad-hoc event parsing보다 converter API를 우선 사용하세요. XPath 1.0 selector와 field transform이 selector 중심 `if` 로직 대부분을 흡수합니다. `EventReaderSync`는 가벼운 전체 XML 순회에 남기고, `ProjectionReader`는 무거운 unknown-schema materialization이나 여전히 stream-imperative인 로직에 사용합니다.

현재 fixture:

- `catalog` 문서
- `800`개의 `<featured>` 요소
- `800`개의 `<book>` 요소
- 결과에는 root object field, root array, direct scalar, transform 파생 field가 포함됩니다
- native projection 행은 direct attribute/child-element field만 가진 byte-input
  `<entry>` fixture를 사용하고, JS/native JSON output 동일성을 먼저 확인합니다
- `ProjectionReader` 행은 같은 row count와 column shape를 확인하지만, JSON
  object materialization이 아니라 lower-level columnar surface를 측정합니다

<BenchmarkSection locale="ko" section="converter" />

해석:

- 순수 처리량 기준 최상한은 여전히 handwritten plain parser입니다.
- 일반 converter API는 dispatch-friendly schema를 projection backend로 자동 route하고 schema object에 plan을 cache합니다.
- `.compile()`은 같은 output contract를 유지하면서 dispatch 선택을 명시적이고 재사용 가능하게 만듭니다.
- XPath 1.0 selector와 field transform은 대부분의 구조적 branch logic을 덮을 수 있지만, stream-order control, side effect, early-stop traversal은 여전히 StAX reader surface의 역할입니다.
- byte input과 projection 가능한 compiled schema에서는 per-event JavaScript
  dispatch를 건너뛰고 public native projection surface에 row projection을
  위임할 수 있습니다.
- `ProjectionReader`는 converter hydration 전 native wrapper 비용을 보여줍니다.
  columnar row data가 public output shape로 충분한 경우 이 경로를 사용합니다.

## 성능 팁

### 최적화 전략

1. **올바른 파서 선택**
   - 10MB 미만 문서에는 `StaxXmlParserSync` 사용
   - 대용량 파일이나 스트리밍 시나리오에는 `StaxXmlParser` 사용

2. **메모리 할당 최소화**
   - 이벤트를 저장하지 말고 도착 즉시 처리
   - 자주 생성되는 객체에 객체 풀링 사용
   - 핫 패스에서 문자열 연결 피하기

3. **효율적인 이벤트 처리**
   - if-else 체인 대신 switch 문 사용
   - 파싱 루프 밖에서 정규 표현식 미리 컴파일
   - 배열 대신 Set을 사용하여 요소 이름 조회

4. **스트리밍 모범 사례**
   - 적절한 청크 크기 구성 (기본값 64KB)
   - 라이터에 백프레셔 처리 구현
   - 논블로킹 처리를 위해 비동기 반복 사용

### 성능 모니터링

```typescript
import { StaxXmlParserSync, XmlEventType } from 'stax-xml';

function benchmarkParsing(xml: string, iterations: number = 1000) {
  const start = performance.now();

  for (let i = 0; i < iterations; i++) {
    const parser = new StaxXmlParserSync(xml);
    let eventCount = 0;

    for (const event of parser) {
      eventCount++;
    }
  }

  const end = performance.now();
  const totalTime = end - start;
  const avgTime = totalTime / iterations;
  const opsPerSec = 1000 / avgTime;

  console.log(`파싱당 평균 시간: ${avgTime.toFixed(2)}ms`);
  console.log(`초당 작업 수: ${opsPerSec.toFixed(0)}`);
}
```
