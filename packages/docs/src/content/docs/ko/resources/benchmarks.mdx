StAX-XML의 벤치마크 기준은 pure JavaScript parser입니다. `latest` 문서와
`v1.0.0-rc3` release benchmark set은 같은 계약을 사용합니다. 사용자가
JavaScript에서 실제 호출하는 public surface를 full JavaScript string/object
materialization 기준으로 측정합니다.

## 실행 대상

- `pnpm --dir packages/benchmark bench:sync`: 동기 parser와 builder 경로.
- `pnpm --dir packages/benchmark bench:async`: 비동기 parser와 writer 경로.
- `pnpm --dir packages/benchmark bench:runtime-matrix`: Node, Bun, Deno가
  설치되어 있을 때 동일한 JavaScript reader workload를 runtime별로 비교.
- `pnpm --filter benchmark run release:expanded`: release runtime matrix와
  4 GiB `StreamReaderSync` index-first benchmark, converter compiled
  batch-plan benchmark, 그리고 1 GiB writer benchmark artifact를 다시 생성.

## 계약

Parser benchmark는 JavaScript string과 JavaScript object를 반환합니다.
native addon, Wasm parser module, binary parser aggregation, backend mode
fallback은 사용하지 않습니다. 대용량 XML 확인은 낮은 RSS, JavaScript string
크기 제한 회피, stream/event/converter API를 통한 pull 방식 소비를 기준으로
유지합니다.

이 pure JavaScript 계약은 native/Wasm/backend row만 제거합니다. Native 결정과
무관한 benchmark track을 폐기한다는 뜻은 아닙니다. Parser, stream reader,
converter, builder, writer, async writer, large writer sink benchmark는 계속
별도 측정 surface로 유지합니다.

사용합니다.

## 다른 Benchmark Track

Native/Wasm 결정은 writer와 builder benchmark 계약을 바꾸지 않습니다.

| Track | Command | 측정 내용 |
| --- | --- | --- |
| Parser fixture series | `pnpm --dir packages/benchmark bench:sync` | 2 KiB, 4 KiB, 13 MiB, 98 MiB parser fixture와 sync builder row. |
| Builder small/large | `pnpm --dir packages/benchmark bench:builder:small`, `bench:builder:big` | Builder-friendly intermediate data에서 XML emission. |
| Converter compiled batch plan | `pnpm --dir packages/benchmark bench:converter:compiled-batch` | Manual `StreamReaderSync` projection과 converter auto-lowered/명시적 `.compile()` batch dispatch plan 비교. |
| Async parser/writer | `pnpm --dir packages/benchmark bench:async` | Async parser와 async-vs-sync writer API overhead. |
| Writer core | `pnpm --dir packages/benchmark bench:writer:core` | Compact/pretty output에 대한 direct writer method throughput. |
| 1 GiB writer | `pnpm --dir packages/benchmark bench:writer:1gb:json` | Memory/temp-file target 위의 async writer와 sync sink writer. |

대용량 XML 출력에서 전체 XML string을 보관하지 않고 incremental write가 필요하면
`WriterSyncSink`가 계속 권장 synchronous path입니다. Release artifact는 1 GiB
writer 결과를 `packages/benchmark/results/release/raw/writer-1gb.json`에 보존합니다.

## Converter API 비교

Converter 비교는 pure JavaScript release contract의 일부입니다. Native projection
reader를 호출하지 않습니다. Manual baseline은 `StreamReaderSync` batch를
`eventCount`와 index accessor로 소비합니다. Converter row는 같은 byte fixture를
다음 경로로 파싱합니다.

- `schema.parseSync(bytes)`: 지원 가능한 schema를 compiled dispatch batch plan으로
  자동 lowering합니다.
- `schema.compile().parseSync(bytes)`: 같은 compiled batch plan을 명시적으로 만들고
  재사용합니다.

두 converter row는 측정 전에 manual projection과 동일한 결과를 만드는지 검증합니다.
Release artifact는
`packages/benchmark/results/release/converter-compiled-batch-plan.json`입니다.

| Case | Throughput | Average | Books | Checksum |
| --- | ---: | ---: | ---: | ---: |
| Manual `StreamReaderSync` projection | 80.17 MiB/s | 199.58 ms | 139,458 | -1845341048 |
| Converter `schema.parseSync(bytes)` | 47.11 MiB/s | 339.63 ms | 139,458 | -1845341048 |
| Converter `schema.compile().parseSync(bytes)` | 46.03 MiB/s | 347.61 ms | 139,458 | -1845341048 |

## StreamReaderSync 소비 방식

대용량 byte input에서는 batch-local index access를 권장합니다.

```ts
import { StreamEventType, StreamReaderSync } from 'stax-xml';

const reader = new StreamReaderSync(byteBatches);

for (const batch of reader) {
  for (let index = 0; index < batch.eventCount; index++) {
    if (batch.typeAt(index) === StreamEventType.START_ELEMENT) {
      const name = batch.nameAt(index);
      const attributeCount = batch.attributeCountAt(index);

      for (let attribute = 0; attribute < attributeCount; attribute++) {
        const attributeName = batch.attributeNameAt(index, attribute);
        const attributeValue = batch.attributeValueAt(index, attribute);
        consume(name, attributeName, attributeValue);
      }
    }
  }
}
```

`for (const event of batch)`도 계속 지원하지만 wrapper event object를
할당합니다. Canonical 98 MiB fixture에서 index-first 소비는 730.56 ms,
heap delta 약 39.8 MiB였고, wrapper iteration은 1.28 s, heap delta 약
482.7 MiB였습니다.

## Native와 Wasm을 제거한 이유

Native 또는 Wasm code는 XML byte tokenize를 빠르게 할 수 있습니다. 하지만
public JavaScript API는 결국 JavaScript string과 object를 반환해야 합니다.
JavaScript string은 재사용 가능한 `char[]` view가 아니라 immutable primitive입니다.
Native addon이 JavaScript-owned byte를 읽는 것은 가능하지만, 파싱된 name,
text, attribute, event object가 JavaScript로 돌아오는 순간 decode, allocation,
wrapper, ownership 비용을 피할 수 없습니다. Wasm도 별도의 linear memory를
가지므로 같은 materialization boundary를 만납니다.

그 bridge 비용 때문에 full public workload는 pure JavaScript path에 가까워졌고,
native heap 또는 Wasm memory는 RSS를 증가시켰습니다. 그래서 StAX-XML은
native/Wasm backend mode를 제거하고, 낮은 메모리, 대용량 XML, pull 방식 소비를
위한 portable pure JavaScript parser에 집중합니다.
